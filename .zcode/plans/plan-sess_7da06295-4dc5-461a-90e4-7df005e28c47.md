# Integrate Skye's Progressive Point-Cloud Rendering into Splatshop

## Goal
Bring Skye's "progressive real-time rendering of massive point clouds" technique (paper: Schütz et al. 2019) into Splatshop as a first-class render path, **ported to CUDA** so it fits the engine's existing CUDA-first point pipeline. The `E:\Code\Skye` repo is the **reference implementation only** (it is OpenGL 4.5 + V8/JS, NVIDIA-only) — no Skye code is linked; its algorithms are reimplemented as CUDA kernels.

## Key finding that shapes the plan
Splatshop **already has** a CUDA point renderer that matches Skye's `compute_hqs` path:
- `SNPoints` (`src/scene/SNPoints.h`) → `Points` (`include/Points.h`) → `PointDataManager`/`PointData` (`src/PointsManagement.h`, `src/HostDeviceInterface.h:343`)
- `kernel_hqs_depth` / `kernel_hqs_color` / `kernel_hqs_normalize` in `src/render/points.cu` (atomicMin depth → atomicAdd color → resolve), dispatched in `src/SplatEditor_draw.h:1477-1505`
- A working `.las` loader (`src/loader/LASLoader.h`) and per-frame point upload (`src/SplatEditor_update.h:194-213`)
- `RenderTarget.framebuffer` (`uint64_t*`, `(depth<<32)|color`) and an existing `RenderTarget.indexbuffer` (`uint64_t*`, used for splat selection)

This existing renderer draws **all points every frame** — it does not scale to hundreds of millions / billions. **Skye's contribution is exactly what is missing:** load-time prime-permutation shuffle, reprojection, budgeted hole-fill, and VBO rebuild via a per-pixel index image. So this integration *adds* the progressive path alongside HQS, reusing the existing data model and framebuffer convention.

Confirmed choices: **Port to CUDA** · **Full scope** (reproject + fill + VBO rebuild + adaptive budget + multi-buffer) · **Formats: `.las`, `.bin`, `.ply` (point cloud)**.

---

## Architecture

- Reuse `SNPoints`/`Points`/`PointDataManager` as the data node. Add an optional **progressive data block** to `SNPoints` (shuffled chunk buffers + prime + fill cursor), populated at load, used only when progressive rendering is active. The HQS path stays unchanged.
- Progressive **render state is per-target** (cached like `ConcurrentTarget`): a reproject VBO, a per-pixel index image, an indirect count, and CUDA-event timing. Stored in a `static vector<ProgressiveTarget>` cache inside `draw()`.
- Progressive kernels write into `target.framebuffer` using the same `(depth<<32)|color` + `atomicMin` convention as HQS, so EDL post-processing and the final GL blit work unmodified.
- New `.cu`/`.h`/`.cpp` files are **auto-globbed** (`src/render/*.*`, `src/scene/*.*`, `src/loader/*.*` with `CONFIGURE_DEPENDS`) — no `CMakeLists.txt` change needed. The only manual wiring is registering one `CudaModularProgram` and declaring a few members.

## New files

### `src/render/progressive_points.cu` (core — port of Skye's `modules/progressive/` shaders)
CUDA kernels (extern "C" `__global__`, matching `points.cu` style and `CommonLaunchArgs`):
1. `kernel_progressive_distribute` — port of `distribute.cs`. Prime-permutation scatter: `targetIndex = permuteI(permuteI(globalIndex, prime), prime)`; routes `{pos,color}` into the correct chunk by `targetIndex / MAX_POINTS_PER_BUFFER` (MAX = 134,000,000). Multi-buffer faithful to Skye.
2. `kernel_progressive_reproject` — port of `reproject.vs/fs`. One thread per entry of last frame's reproject VBO (`indirectCount` entries). Project by `proj*view*transform`, write `(depth<<32)|color` to `target.framebuffer` via `atomicMin`, write packed 32-bit global point ID to `indexImage[pixelID]`. 1px points; discard off-screen/uninitialized.
3. `kernel_progressive_fill` — port of `fill.vs/fs`. One thread per point in `[fillOffset, fillOffset+budget)` (wraps, multi-buffer routed). Same framebuffer + indexImage writes; discards uninitialized points; advances `fillOffset`.
4. `kernel_progressive_create_vbo` — port of `create_vbo.cs`. 16×16 workgroups, one thread per pixel. Reads point ID from `indexImage`; if non-empty, `atomicAdd` a compaction counter, fetches `{pos,color,globalID}` from the right chunk, stores into `reprojectVBO[counter]`; the counter becomes next frame's `indirectCount`. Resets `indexImage`.
5. `kernel_progressive_clear_index` — clears `indexImage` before reproject+fill.
6. `kernel_progressive_compute_fill` — port of `compute_fill.cs`/`compute_fill_fixed.cs`. **Adaptive budget**: uses CUDA events (replacing GL timestamp queries) to measure reproject+fill time, estimate `pointsPerMillie`, and write the remaining-budget fill count for a target frame time.

### `src/loader/BINPointCloudLoader.h`
Port of Skye's `ProgressiveBINLoader` fast path: `.bin` = 16 bytes/point `{float3 pos, uint32 rgba}`. Streams directly into `Points::position`/`color` (no parsing). High throughput.

### `src/loader/PointCloudPlyLoader.h`
Point-cloud PLY reader (distinct from `GSPlyLoader`, which is gaussian-splat PLY with scale/rot/SH). Parses the PLY header for `vertex` properties `x y z [r g b]`, fills `Points`. Detects point vs splat PLY by absence of `scale_*/rot_*` properties.

### `src/scene/SNPoints_progressive.h` (or inline in `SNPoints.h`)
A `ProgressivePointData` struct + helpers: `vector<shared_ptr<CudaVirtualMemory>> chunkPos, chunkColor; uint64_t chunkCapacity=134'000'000; uint64_t prime; uint32_t fillOffset; bool ready;` plus `initProgressive(numPoints)` (compute prime, allocate chunks) and a `distribute` launcher. Prime computed on host by porting Skye's `previousPrimeCongruent3mod4` (`ProgressiveLoader.h:45-74`, tiny pure C++).

## Phasing

**Phase 1 — Working progressive (core):** `progressive_points.cu` with distribute/reproject/fill/create_vbo/clear_index; `ProgressiveTarget` cache; `SNPoints` progressive data + load-time shuffle; render branch with **fixed** budget; `.las` + `.bin` loaders; drag&drop; basic GUI (toggle + budget + reset). Start single-buffer, then enable the multi-buffer chunk scheme.

**Phase 2 — Full scope:** multi-buffer chunk routing finalized; adaptive-budget kernel via CUDA events; `.ply` point loader + File-menu load dialog; integrate progressive path with EDL; (optional) port Skye's multi-threaded streaming LAS loader for higher throughput.

**Phase 3 — Polish:** per-node reproject VBOs so multiple progressive clouds can render simultaneously; prime-shuffle during incremental upload (streaming huge clouds without waiting for full load); timings/stats panel; README documentation.

## Out of scope (noted, not touched)
- The pre-existing 4DGS work (`SN4DGSSplats`) has a bug: `swapToCanonical()` is called at `SplatEditor_draw.h:1384-1387`, **before** the splat dispatch at 1646-1663, so deformed geometry is never rasterized; deformed opacity is also computed but not swapped. This is unrelated to point clouds and will be left as-is (flagged for the user).

Test with a >134M-point cloud to exercise multi-buffer routing.
