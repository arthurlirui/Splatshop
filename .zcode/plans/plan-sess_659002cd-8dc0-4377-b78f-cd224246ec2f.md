# VR 远程浏览三维场景 + 头盔运动驱动渲染 — 设计方案

## 核心结论：复用已有能力，新增"外部位姿"路径

经过探索，本仓库**已经具备完整的本地立体 VR 渲染管线**（OpenVR，`SplatEditor_render.h:31-195` 双目渲染、`SplatEditor_update.h:393-403` 位姿装配、`:580-597` 提交到 HMD），且 CUDA 光栅化器本身是立体无关的（`RenderTarget` 携带逐眼 `view/proj/VP` + `isLeft/isRight`，`HostDeviceInterface.h:485-495`）。远程 API（`RemoteControlServer.cpp`）目前是**纯控制平面**，只驱动桌面 OrbitControls，且**完全没有视频回传通道**（`docs/remote_api.md:33-35` 明确说明控制与视频分离）。

因此本设计 = **(A) 新增"外部位姿"双目渲染路径**（复用现有渲染器，绕开 OpenVR 的本地 HMD）**+ (B) 新增视频回传通道**（当前完全缺失）**+ (C) 扩展远程 API 传递 6DOF 位姿**。客户端以**独立头显通过浏览器 WebXR** 为主目标（与现有 browser/Python HTTP 架构天然契合），协议设计成平台无关，PC VR 客户端也可对接。

---

## 架构总览

```
[VR 头显(独立机/PC)] ──浏览器 WebXR 读取位姿──> [Python FastAPI :8080]
                                                      │ HTTP/JSON(位姿,逐眼投影)
                                                      ▼
                                          [C++ RemoteControlServer :7654]
                                                      │ JSON-RPC / 持久流
                                                      ▼ EventQueue(主线程)
        ┌─────────────────────────────────────────────┴──────────────────────┐
        │ 新增 VIEWMODE_REMOTE_STEREO 分支                                       │
        │   viewLeft/Right.view = inverse(flip * remoteHeadPose * remoteEyeOffset)
        │   viewLeft/Right.proj/VP = remotePerEyeProjection (翻转Y轴后)         │
        └─────────────────────────────────────────────┬──────────────────────┘
                                                      ▼ 复用现有双目渲染
                                          [CUDA 双目光栅化 → viewLeft/Right.framebuffer]
                                                      │ 新增回读+NVENC编码
                                                      ▼
                                          [H.264 码流 → WebRTC/WS 推送]
                                                      ▼
                                          [浏览器 WebCodecs 解码 → WebXR display]
```

控制流（位姿上传）走现有 HTTP/JSON 通道（高频小包，<1KB/帧）；视频流（眼睛帧回传）走**新增**的高吞吐通道。两条通道解耦，符合现有"控制/视频分离"的既有设计哲学。

## 关键设计决策与依据

### 1. 位姿坐标变换（最易出错点，需重点说明）
现有 `flip` 矩阵（`OrbitControls.h:148`、`SplatEditor_update.h:56`）把 OpenVR 的 +Y上/+Z前 追踪空间转到本应用 +Z上/+Y前 的 GL 空间。现有装配为 `inverse(flip * poseHMD * poseEye)`（`:397`）。
- **WebXR 客户端**：WebXR 的 `XRRigidTransform`/视图矩阵已在 +Y上/+Z前 空间，且视图矩阵本身就是 world→eye。服务端**不能再乘 `flip`**，而是直接 `view = remoteViewMatrix`（或对位置/四元数自行装配，跳过 flip）。
- **PC VR 客户端(SteamVR)**：直接发 OpenVR `dmat4`，服务端套用现有 `flip` 逻辑。
- 因此协议字段需带一个 `pose_space` 标志（`"openvr"` / `"webxr"` / `"raw_view"`），服务端据此决定是否施加 flip 与求逆。这是协议设计的核心约束，避免重蹈 `cmd_mouse_move` Y 翻转那类隐式约定陷阱（`RemoteControlServer.cpp:281` 已有先例）。

### 2. 复用现有 `RenderTarget`/`View` 机制，不碰光栅化器
现有双目就是"对 `viewLeft`/`viewRight` 各跑一遍 `draw()`"（`SplatEditor_render.h:50-195`）。外部位姿只需在 `SplatEditor_update.h` 的新分支里填好 `viewLeft/Right.{view,proj,VP}`，渲染路径几乎不动。`isLeft/isRight` 标志与 `Uniforms.vrEnabled` 已被内核正确处理（`gaussians_rendering.cu:509`）。

### 3. 提交到 HMD 的跳过
`SplatEditor_render.h:580` 的 `if(viewmode == VIEWMODE_IMMERSIVE_VR && ovr->isActive())` 会向本地 OpenVR 提交纹理。新模式下本地无 HMD，必须**跳过此块**（条件改为 `&& ovr->isActive()`，新模式下 `ovr` 未启动，自然跳过）。

### 4. 视频回传：NVENC 硬编 + WebRTC/WS（主选）
当前无任何编码/流代码。新增一条最小依赖路径：
- 服务端把 `viewLeft/Right.framebuffer` 的 GL 纹理（已通过 `cudaSurfaceObject` 映射，见 `SplatEditor.h:83-106` 的 `mapCudaGl`）经 NVENC 编 H.264。
- 经 WebRTC（datachannel/video）或 WebSocket 推送到浏览器。
- 浏览器用 WebCodecs 解码 → 送 WebXR `XRWebGLLayer` 或 canvas。
- 理由：VR 需 <50ms 动作-光子延迟，软编/JPEG 链路无法达标；NVENC 复用服务端现有 CUDA 上下文，依赖最轻。
- 阶段化：先做 SBS（左右并排）单流简化实现，再优化为逐眼双流。

### 5. 部署范围：先 LAN 后 WAN
LAN 优先（实验室/演播室低延迟），协议层预留拥塞控制与码率自适应扩展点，后续可扩 WAN。

## 实施步骤

### 阶段 1：外部位姿渲染路径（C++ 侧，无网络）
1. **`src/common.h`**：新增 `constexpr int VIEWMODE_REMOTE_STEREO = 3;`。
2. **新增位姿缓冲**：在 `SplatEditor.h` 加 `struct RemoteStereoState { dmat4 headPose; dmat4 eyeLeft, eyeRight; dmat4 projLeft, projRight, vpLeft, vpRight; int width, height; PoseSpace space; bool fresh; }`，主线程读、远程线程写，用 `std::atomic`/`mutex` 保护（参照 `OrbbecCapture` 的 mutex 模式）。
3. **`SplatEditor_update.h:371`**：在 `if(viewmode == VIEWMODE_IMMERSIVE_VR)` 旁加 `else if(viewmode == VIEWMODE_REMOTE_STEREO)` 分支，从 `RemoteStereoState` 装配 `viewLeft/Right`，按 `space` 决定是否乘 `flip`/求逆，并 resize 4096 framebuffer 至远程分辨率。
4. **`SplatEditor_render.h:31`**：把 `if(ovr->isActive())` 的双目渲染分支条件扩展为 `if(ovr->isActive() || viewmode == VIEWMODE_REMOTE_STEREO)`，复用同一套逐眼 `draw()`；`:580` 的提交块保持 `ovr->isActive()` 不变（新模式自动跳过）。
5. 验证：用一段录制好的位姿序列（复用 `OpenVRHelper` 的 keyframe 录制格式，`OpenVRHelper.h:178`）回放，确认双目渲染正确、无翻转。

### 阶段 2：扩展远程 API 传位姿
6. **`RemoteControlServer.cpp`**：新增 `cmd_vr_pose` 命令（高频，每帧/每 N ms 一次），写入 `RemoteStereoState`；入 `handlers()` 表（`:707`）。
7. **协议**（`models.py` 镜像）：字段 `head_pose`(4x4 或 [quat(w,x,y,z)+pos])、`eye_left/right`(4x4)、`proj_left/right`(4x4 或 tan-angles)、`width`/`height`、`pose_space`、`timestamp`。考虑高频，提供两种载入方式：单次 `camera.vr_pose`（沿用现有同步 RPC）+ 可选持久流（见阶段 4）。
8. **`server.py`**：新增 `POST /vr/pose`，透传给 C++；可选 `GET /vr/frame_stream` 视频端点。

### 阶段 3：视频回传通道（C++ 侧，最大工作量）
9. **新增 `src/remote/FrameStreamer.h/.cpp`**：NVENC 编码 `viewLeft/Right` 纹理（复用 `mapCudaGl` 拿到 CUDA 可访问的纹理），输出 H.264 NAL。帧节奏由主渲染循环驱动（`SplatEditor_render.h` 末尾，提交块之后）。
10. **传输**：二选一——(a) 内嵌轻量 WebRTC（如 libdatachannel，纯 C++，无重依赖）直接推 video track；(b) WebSocket 推 H.264 NAL，浏览器 WebCodecs 解码。建议先 (b)（依赖更少、可控），后迁 (a)。
11. **CMakeLists.txt**：加 `ADD_FRAMETREAMER`（仿 `ADD_ORBBEC` 静默缺失模式），链 NVENC（CUDA 已在，仅需 `nvidia-encode`），可选 libdatachannel。

### 阶段 4：客户端（浏览器 WebXR）
12. **`remote_api/` 新增 `vr_client.html`/`.js`**：用 WebXR `requestSession({optionalFeatures:['local-floor']})` 读 `XRFrame.getViewerPose()`，逐帧从 `getViews()` 取 viewMatrix + projectionMatrix → POST `/vr/pose`。
13. **视频接收**：WebSocket 接 H.264 → `VideoDecoder`(WebCodecs) → 绘到 WebXR `baseLayer` 的 WebGL framebuffer（左/右 view 各画半屏）。
14. 同步：位姿时间戳与帧时间戳对齐，处理抖动缓冲（先做简单最新帧策略）。

### 阶段 5：集成验证与文档
15. 端到端跑通：头动 → 位姿上行 → 双目渲染 → 视频下行 → 头显显示，测量动作-光子延迟。
16. 更新 `docs/remote_api.md`（新增 VR 章节）、`README.md`（VR 远程浏览功能说明）。

## 不改动 / 明确边界
- **不动** CUDA 光栅化内核、`RenderTarget`/`Uniforms` 结构、`draw()` 主体、桌面 OrbitControls 路径。
- **不动** Orbbec 模块（确认与 VR 无关，仅 RGBD）。
- **不破坏** 现有 `ovr->isActive()` 的本地 VR 路径（新模式与之并列）。
- 视频通道是**新增**，不强行塞进现有同步 RPC（`runOnMainThread` 的 10s 超时与单帧阻塞模型不适合流）。

## 风险点
- 延迟：NVENC 编码 + WebRTC/WS + 解码 + WebXR 合成，累积可能 >50ms；需测真实链路，必要时降分辨率/帧率。
- 位姿空间一致性：`flip` 与 WebXR/OpenVR 坐标系差异是最大正确性风险，必须有 `pose_space` 显式标志 + 阶段 1 的离线回放验证。
- WebRTC 依赖体积：若选 libdatachannel 需评估编译/部署成本；可先用 WS+WebCodecs 走通再迁移。
- 浏览器 WebXR 对非 HTTPS 限制：localhost 例外，远端访问需 HTTPS/反向代理（与现有 CORS 全开策略一致，但需补 TLS）。
